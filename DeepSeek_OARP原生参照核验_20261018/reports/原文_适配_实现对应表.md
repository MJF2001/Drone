## 二、本轮新增的原生结构（原文未给数据结构，属实现）

| 项 | 实现 | 强度 |
|---|---|---|
| 条带身份 `rank_id`、轴向、规范格序列 | `native.Strip` | 实现解释（来源是 rank 求解结果 + tour 次序，**不**从逐格首访反推） |
| 服务段/连接段路线索引 | `native.build_plan` 建路线时**当场写入** | 实现解释 |
| 执行事实（前缀、当前位置、首次覆盖索引、步数） | `native.Execution` | 实现解释 |
| 事件后状态 P/F/C/Q/D | `native.event_state` | 适配（任务定义来自项目） |
| 剩余片段规范化 + 原因 | `native.normalize` | 适配（见下） |

**规范化规则**（每条都有原因字段）：

1. 已完成的条带整段删除（`completed`），原方向不因此改变；
2. 部分执行只删已覆盖格，剩余格保留原 `rank_id`、原路线索引、原轴向（`partially_executed`）；
3. 中间被覆盖切开时，按连续段拆成多个片段，各自带原 `rank_id` 与原索引（`split_by_coverage`）；
4. 竖条带只剩一格仍是 V（轴向来自原生记录，不按几何重猜）；
5. 新障碍造成的切分只在事件后发生，不提前混入事件前的参考；
6. D（被障碍遮挡的已发布目标）保留、不作业、不飞入。

## 三、两个参照的差异（必须是真的不同方法）

| | `OARP_RANK0_FULLTOUR_SCENE` | `OARP_REPLAN2_NATIVE_SCENE` |
|---|---|---|
| 条带模型 | variant 0，无改变预算 | variant 2，`cap` 显式给定（0 / 2 / 2·\|Q\|） |
| 旧条带输入 | **不传**旧 services | 传原生剩余片段（身份、轴向、原索引） |
| 未变块内部顺序 | 全部重排 | 保留原块内部连接（`path_sets` 的 path 块） |
| 旧路线 | 不读 | 只在保留块内按其原索引取连接，并与当前 F 校验 |
| 名字含义 | 本场景的整体条带参照 | 模型 2 + 旧块复用的原生参照 |

“只调大 cap”不构成整体重排：rank0 版本在代码里根本没有 old services；replan2 版本即使 `cap=2·|Q|` 仍会保留未变块——两者不是同一个方法。

## 五、成功、核心完成与自然终止（D2）

旧的 `OARP_CORE2` 适配器把“外层 `finished`”当自然完成。本轮拆成独立字段：
`route_valid`、`coverage_complete`、`resource_valid`、`returned_base`、`rank_status`、
`rank_optimal`、`tour_status`、`core_candidate_valid`、`fallback_selected`、`natural`、
`termination_reason`、`call_within_budget`、`candidate_accepted_in_time`。

- rank 触时限但有整数解、GLNS 触时限但有用路线、人工看门狗、核心无解只返保底：
  这些都不再由外层状态表示“核心自然完成”；
- `tour_status=converged` 只表示 GLNS 未报 timeout，**不表示最优**。
