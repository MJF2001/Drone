# 认证修复核查

## 1. 它是什么

冻结实现里的 `rank_replan(..., allow_certification_repair=True)`：当 LP/MIP 的整数解
解码后不能覆盖全部格（或目标值与解码值不符）时，代码**重新求解一个加强模型**
（`_certified=True`），并记录 `certification_repair=True` 与原拒绝解。

加强项（`ranks.py::_build` 中 `certified` 分支）：

- 每个带方向的格必须被恰好一条选中的区间覆盖：
  `sum{covering intervals} == orientation[axis,p]`；
- `endpoint[axis,side,p] <= orientation[axis,p]`；
- 轴端强制：`L` 端点在没有前驱时取 1，`R` 端点在没有后继时取 1。

**必须说清的三件事**：

1. 这些约束对"任意真实整数条带划分"都成立，所以是**合理的物理一致性加强**；
2. 加强前后的 LP 可行域**不同**，所以不能称"修复后仍与原 LP 完全一样"；
3. 这是**我们实现**的加强，不是作者程序的运行结果，也不能据此判原文错误。

## 2. 本轮实测

42 个独立条带子问题（10 个冻结输入 × cap 0/1/2/6 全部开启认证 + 2 个关闭认证的严格诊断）：

| 项 | 结果 |
|---|---|
| 子问题总数 | 42（40 + 2） |
| 与独立枚举一致 | **42/42** |
| 触发认证修复 | **1 次**（`diag_three_to_four_cap1` 之前的同类三格扩四格情形） |
| 关闭认证后的严格诊断 | `diag_three_to_four_cap1` 返回 `invalid_original_model_solution`（未加强模型给出无法解码的整数解），与独立枚举"cap=1 时无可行划分"一致 |
| `diag_unchanged_line_cap0` | 与枚举一致（零改变可行） |

**独立参照**是 `tools/run_math.py::enumerate_partitions`：枚举每个格的方向
（H/V）**以及每对同向相邻格之间是否切开**，再按冻结的 `metrics` 计算
`rank_count + endpoint_bound/(cap+1)`。第一版枚举只取"最大连续段"，漏掉了
"同向但切开"的划分——正是保留旧块需要的那种——已被修正；这条修正本身说明
"用生产 `partition` 枚举当参照"会自证成立。

## 3. 触发例的代数解释

三格旧条带（同一行 0、1、2）加第 3 格、cap=1 时：

- 合法地扩成四格条带：新增右端点 R3、移除原右端点 R2、方向保持 →
  `changed = 1 + 1/2 = 1.5 > 1`，模型 2 不允许；
- 未加强模型给出 objective=2 的整数解，但解码从 L0 走到 R2 就停，漏掉第 3 格；
- 这是"相邻差分下界没有排除不成对端点"的代数漏洞；加强约束可以排除它。

**边界**：这是本实现、本适配、本小例子里的现象；新增目标也超出原文主要障碍重规划实验。
本轮不能据此判原论文错误，也不把"修复"说成创新。

## 4. 与旧证据的关系

主会话此前的核查已记录同一现象（关闭修复的 40 项中 1 项产生不可解码解）。
本轮独立重跑 40 项（全部开启修复）得到 40/40 一致，并**没有**声称复现了
历史那次关闭修复的日志——那次的原始 SCIP 向量未保存，历史缺口继续保持未知。
