## 2. 适配器为什么必须重写

机制核验版的 `adapter.py` 有三处不能带进生产接口：

1. **状态只由 terminal 决定**：`status = finished if terminal.startswith("FN")`，
   即使 `audit.valid=False` 也不会降级；本轮改为 `finalize` 统一裁决（见 §2.1）。
2. **没有截止**：`request.termination` 从未变成 `Deadline`，MAPS/ETM/连接器/返航/审核
   都没有截止检查；本轮把公共软截止贯穿整个调用（见 §2.2）。
3. **没有登记**：既不经过两阶段账本，也没有候选接受边界。

### 2.1 成功判定

```
route -> finalize(request, route, ...)   # 独立审计：起点/四邻接/覆盖 Q/返航/资源
status = outcome["status"]               # 只有 audit.valid 才会是成功状态
```
- 自然 FN + 审计通过 → `finished`
- 人工截断（步数上限 / state_cycle / no_progress）+ 审计通过 → `finished_with_safety_limit`
  （明确写"有合法解但非自然结束"，不标自然 finished）
- 审计不通过 → `coverage_incomplete` / `resource_exceeded` / `invalid_route`
- 环境不可行 → `environment_infeasible`；输入矛盾 → `input_precondition_unmet`

### 2.2 截止与候选接受边界

```
deadline = Deadline(request.time_limit)
检查点：入口 -> MAPS 构造(逐格) -> 每轮控制 -> 连接器前 -> 连接器后 -> 返航前/中 -> 审核前
audited = deadline.elapsed()
if audited > limit:            # 审核跨截止
    route 清空，保留 diagnostic_route（带 source）
    status = deadline_before_complete_route
```
- 候选三态写进 `meta.candidate`：`generated / audited / accepted / post_deadline`
- `meta.deadline` 最后写入，含真实 `checks / elapsed / hit`
- 多因素分开：`audit`（事实）、`termination`（引擎原因）、`not_scorable_reason`（为何不计成绩）

### 2.3 时间边界

- `call_total`（注册表外层墙钟）包含输入核验、MAPS、ETM、连接器、返航、审核；
- 两阶段账本的写与 fsync 在计时之外，单独可查；
- 子进程启动由父进程单列。

## 3. 输入校验的唯一再放行

sealed 的 `validate_inputs` 拒绝任何 `remaining_resource <= 0`。
本轮空任务案例需要 `资源 0 + 人在基地 + Q 空` 合法成功（0 步即可完成）。
处理：**不改 sealed 模块**，在 `src/inputs.py` 包装里只放行这一种组合，
并把放行记录写进 `soft` 字段（`resource_zero_empty_task_at_base`）。

- 资源 0 但 Q 非空 → 仍然拒绝（`test_resource_zero_with_a_task_is_still_rejected`）
- 资源 0 但不在基地 → 仍然拒绝
- 位置不在 free → `current_not_free`

## 4. 只改文档、不改代码的地方

| 旧说法 | 本轮改为 |
|---|---|
| "转角项必须非零" | 改为实验条件下观察到的震荡/截断；`state_cycle` 键不含 RNG，不能证明永久不终止 |
| "只对 Q 正势会改变 B 均值" | 改为只改变 p^U；B 均值由块几何决定（有测试） |
| "每次调用都整图 BFS" | 改为连接器有缓存：区分调用次数、缓存命中与实际 BFS 行（`core.etm.connector_stats`） |
| "已保留 Theorem 1" | 改为只保留"每格只作业一次"的规则；20 次微图自然结束不构成本模型下定理的证明 |
| "7×5 / 9×3 是原文规定" | 改标为实现解释/扩展；覆盖与互斥只证明铺砌性质 |
| "完整原文复现" | 版本名与报告都写明不是完整复现（`not_claimed` 字段） |

## 5. 行为影响（交付批 24 次实测）

| 观察 | 数值 |
|---|---|
| 成功 | 18/24（`finished`），审计全部合法 |
| 环境不可行 | 2（8×8 分量被墙隔开的用例） |
| 资源超限 | 2（空任务、距基地 2 步、资源 1） |
| 输入拒绝 | 2（当前位置不在 free） |
| 硬看门狗终止 | 0 |
| 物理覆盖早于控制 FN 的额外步数 | 交付批全部为 **0**（`extra_steps_physical_to_fn=0`） |
| 连接器 BFS 行 vs 路径调用 | 例：环形图 63 行 / 72 次路径调用 → 缓存确实在被用 |

**额外步数为 0 说明什么**：在 `task` 模式下，物理覆盖与控制待处理在扫掠过程中同步推进，
没有出现"物理已完成但控制仍扫掠"的长尾。这是本轮小图的事实，**不能**外推到大图；
大图上是否出现长尾需要下一轮按预定范围测。

## 6. 与旧版 ε* 的关系

- 旧版（`transit` + `turn_cost=0`）的核心不再作为候选：控制分支不可达、转角项缺省为 0 已证实改变行为；
- 新版 `epsilon_star_core_integrated_v1_20261018` 是**机制候选**，不是性能结论；
- 旧 300 项对照结果保留，但只能解释为旧实现的行为。
