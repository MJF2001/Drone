# 第一部分：P2 现状诊断（定位到实际代码）

## 1. 冻结 P2_MULTI 到底是什么

`baseline_suite.solve(..., 'P2_MULTI', ...)` → `p2_search_audit.solve(s, budget, 'multi', seed)`。
完整阶段表见 `specs/method_original_mapping.md` §1。要点：

| 环节 | 实际做法 | 代码 |
|---|---|---|
| 初值 | 两种规则扫描序（H/V，按 `2r+1` 足迹间距采样 + 显式贪心补齐）与两种最近邻序 | `planners.candidates`、`planners.nearest` |
| 距离 | 共同几何的精确 BFS 距离；同一对端点只生成一种最短路径 | `unified_geometry.py`、`bfs_metric_geometry.py` |
| 2-opt | 固定起点/终点；每轮取**全局最优改进对**；轮数上限 8（核心）/120（加深）/32（多起点） | `p2_search_audit.opt` |
| 多起点 | 反向扫描序 2 个、每轴 4 次随机区间反转、2 次 `sorted(demand)` 洗牌 | `variant=='multi'` 分支 |
| 候选保留 | `offer` 只接受**完整合法**路线，保留最短，记录来源标签与时刻 | `p2_search_audit.solve.offer` |
| 完整展开 | `Geometry.expand` 对每个相邻访问调用 `path`，并逐格更新覆盖 | `model.py::Geometry.expand` |
| 候选合法性 | 每次 `offer` 都**整条路线逐格重算**（`single_cell_audit`） | `p2_search_audit.offer` |
| 终止 | 墙钟软截止 + 每段轮数上限；截止前有候选 → `planned_at_timeout` | 同上 |

## 2. 版本关系（不能笼统说"都是 P2"）

| 名称 | 是什么 | 证据 |
|---|---|---|
| `P2_MULTI`（冻结 v2） | 上表全部启用（含 120 轮加深与多起点） | `frozen_baselines/v2_20261012/` |
| 第 71—74 轮的 `SEED / PLUS1 / PLUS2 / ALL` | **同一个 P2 引擎**在不同"重排范围 / 责任集合"下的配置；`ALL` 不是另一个求解器 | 报告 71 §"四种范围"，`sources/reports_referenced/71_*.md` |
| `P2_WARM_GLOBAL` | 另一个候选：从旧尾段首次目标顺序启动最多 8 轮全局 2-opt | 报告 70，`candidate_baselines/P2_WARM_GLOBAL/v0.1_20261017/` |
| `P2_SHARED` | `unified_candidates` 里的 P2 入口，供范围诊断复用；与 `P2_MULTI` 共用 `rebuild` | `unified_candidates.py` |

因此"P2 差/好"必须指明是哪一个配置。把它们混在一起比较会重复计算同一引擎。

## 3. 已保存日志能证实什么、不能证实什么

**能证实（有保存记录）**

| 现象 | 来源 | 边界 |
|---|---|---|
| 20 秒预算下 P2 仍有 8/20 次超出名义预算 10 ms 以上，最大约 378.7 ms | 报告 70 §"软超时" | 只说明"20 秒也常被截止打断"，不说明是哪一阶段耗时 |
| P2 的 20 秒最终路线来源分布包含 `reverse_V_raw`(6)、`H_NN_opt`(4)、`V_scan_opt`(2)、`H_scan_opt`(2)、`perturb_V_opt`(2)、`H_NN_raw`(2)、`common_fallback`(2) | 报告 69 表格 | 见下面的二义性 |
| 20 秒 P2 平均求解时间约 12.2 秒（同批 20 次调用） | 报告 70 | 该批是 10 状态×2 预算×2 种子的开发批次，不是性能排名 |

**"raw 来源占 8/20"有两种解释，日志无法区分**

1. 该原始序本身就是最好候选（2-opt 无改进 → 不严格更短 → 来源标签不变）；
2. 搜索预算被别处消耗，优化后的候选根本没来得及提交。

两者对"该改搜索还是该改工程"的结论完全不同。**必须靠插桩区分，不能靠推断。**

**不能证实（缺数据，标缺失）**

- 每阶段的累计耗时：冻结实现把 `events`（含每段 `start/end`）放在返回值里，
  但历史批次**没有**把逐阶段秒数写进结果文件，只写了每个方法的 `seconds`；
- 跨方法的公共时间原点：报告 70 已指出"P2 日志缺公共时间偏移"；
- `OARP_CORE2`、`TREE_MST`、`PPCPP_CORE4` 连阶段事件都没有，只有总秒数；
- 距离查询次数：`Geometry.searches`、`BFSMetricGeometry.bfs_rows_built` 已实现但历史批次未保存。

## 4. 代码级成本结构（这是假设，不是实测结论）

- `offer` 的代价 = O(路线长度)，而且每提交一次候选就要整条重算一次覆盖；
  多起点分支额外提交 12 个初值的 raw 与优化版 → 至少 24 次全路线校验；
- `expand` 对每个相邻访问调用 `path`，若路径尚未缓存就触发一次 A*；
- 2-opt 只用 `distance`（批量 BFS 行缓存），相对便宜；
- 因此"候选数 × 路线长度"可能是主导项，而不是 2-opt 本身。
  这与"20 秒仍未构造完成"的直觉一致，但**本轮没有测量，不能写成事实**。

## 5. 下一轮必须补的插桩点（只在诊断版本，不改冻结算法）

| 插桩点 | 记录内容 | 理由 |
|---|---|---|
| 公共入口单调时钟 | 每次候选接受事件的绝对时刻（同一原点） | 解决报告 70 指出的"缺公共时间偏移" |
| 每阶段累计秒 | 生成 / 最近邻 / 2-opt 每段 / expand / 校验 | 区分"构造慢"与"搜索慢" |
| 距离缓存 | `searches`、`bfs_rows_built`、命中次数 | 判断工程优化空间 |
| expand 与 offer 分开计时 | 展开秒数、校验秒数、覆盖重算秒数 | 判断是否该做增量覆盖 |
| 候选提交次数 | 每个来源的尝试数与接受数 | 区分"没提交"与"提交了但更差" |

插桩版本必须**另立文件名与版本号**，冻结 `p2_search_audit.py` 不改。

# 第二部分：下一轮统一性能比较协议草案（写出，不执行）

## 6. 目标

判断 P2 的质量/耗时瓶颈在哪里，以及应当改进哪个底层方法。
**不是**证明某个预选方法最好。

## 7. 两层规划

### 第 1 层：极小可精确求解实例（名字与正确性验收分开）

- 只选 `exact_reference.exact_optimum` 能在预算内给出 `status='optimal'` 的实例
  （本轮 15 个微图里有 13 个满足，状态数最大 16 304）；
- 报告指标：`steps / optimum`、间隙绝对值与比值、端到端时间；
- 用途：区分"实现错误"与"搜索质量不足"。
- 命名必须与正确性验收分开：这一层的名字带 `exact_gap`，不得与 §8 的
  `dev_snapshot` 混在一张表里。

### 第 2 层：真实执行历史快照（条件化比较）

- 状态来源：既有"连续执行真实历史"开发状态（报告 67/68/69 的 10 个状态），
  每个状态包含：当前公开 `free`、已发布目标 `P`、真实账本 `C`、真实当前位置、
  基地、真实未执行尾段、扣除已走步数后的资源上限；
- 每个方法收到**完全相同**的当前状态，重算"完整剩余任务 + 回基地"，
  **不混入局部范围变化**，不使用留出；
- 边界必须声明：这些历史快照本身来自 P2 的初始计划，因此是**条件化快照比较**，
  不能宣称"整轮端到端执行普遍领先"。

## 8. 样本预定（先列全，再按规则选）

必须**先**列出全部符合条件的开发快照与排除理由，**再**按事件类型/规模预定样本；
不得按"历史上哪个方法赢"来选图。

| 步骤 | 内容 |
|---|---|
| S1 | 列出全部候选快照（来源批次、状态 id、事件类型、规模、当前公开目标数、剩余任务数） |
| S2 | 排除：环境不可行；历史账本与目标不一致；旧尾段缺失且方法有该前提；规模超过任务上限 |
| S3 | 分层：`纯障碍` / `纯扩展` / `叠加` / `无变化`；每层内按剩余任务数分小/中/大三档 |
| S4 | 每层各档取**预定数量**的实例（配额写进协议再开跑），并把最终名单与哈希封存 |

已知的 10 个真实执行状态（报告 69）与 24 张开发基础地图 / 432 状态（报告 45/46）
是候选池；本轮**不**编造具体状态路径。

## 9. 方法版本与资源

| 项 | 取值 |
|---|---|
| 方法 | `P2_MULTI` v2_20261012、`OARP_CORE2` v2_20261012、`TREE_MST` v2_20261012、`PPCPP_CORE4` v0.1_20261014、`EPSILON_STAR` v0.1_20261018、`CSTAR` v0.1_20261018（后两个需先通过各自的忠实性门槛） |
| 硬件 | 记录 CPU 型号、核数、内存、电源模式；同一台机器串行跑，不用并行掩盖耗时 |
| 串行顺序 | 逐实例串行；每个实例内方法顺序**预先**轮换（拉丁方式），避免"先跑的方法吃到冷缓存" |
| 种子 | 每个方法每实例固定 2 个预定种子；重复运行不冒充独立样本 |
| 最大任务数 | 由第 1 层定为 12（精确可解）；第 2 层不设任务数上限但设实例数上限 |
| 总运行上限 | 预先声明总预算与单次上限；触发上限单列，不混入自然结束 |

## 10. 终止条件（逐算法给出，必须区分自然结束与截断）

| 方法 | 自然结束条件 | 已知的截断来源 |
|---|---|---|
| `P2_MULTI` | 4 段核心 2-opt 全部无改进且多起点各段轮数用尽或 `no_improving_2opt_move` | 墙钟软截止 |
| `OARP_CORE2` | LP/MIP 最优 + GTSP 求解器自然收敛 | `cap_for_time` 反查为 `None`、SCIP/GLNS 时限 |
| `TREE_MST` | 单次构造，无迭代 | 几何/展开的软截止 |
| `PPCPP_CORE4` | 核心路线一次走完 | 软截止（`core_status` 会说明是否在截止前通过校验） |
| `EPSILON_STAR` | 某层再也找不到正势（FN）或账本已无待完成 | 步数上限、`state_cycle`、墙钟 |
| `CSTAR` | 无 Open 节点（`graph_exhausted`）或目标已全覆 | 迭代上限、墙钟 |
| `LKH`（未来） | 预定 `MAX_TRIALS` 用尽或自然收敛 | `TIME_LIMIT` |

墙钟触发必须单列为"截断"，**不能**与自然结束混在一列做统计。

## 11. 主表（逐图 + 等权汇总，不只报总步数）

| 列 | 说明 |
|---|---|
| 完整路线步数（含返航） | 主要指标 |
| 端到端计算时间 | 读取后预处理 + 建图/距离 + 初始化/保底 + 求解 + 连接 + 返回前合法检查 |
| 成功率 / 合法率 | 分母含全部任务，不缩减 |
| 自然完成 / 截断 | 分开计数 |
| 保底使用 | 是否最终采用共同保底，保底步数单列 |
| 重复运行波动 | 两个种子的差与幅度 |
| 精确最优（仅第 1 层） | 与 `exact_gap` 同表 |
| 冲突说明 | 若某方法因输入前提被拒，单列原因而不是记 0 |

端到端时间**排除**外部独立事后审计，但必须单列审计耗时。

## 12. 同预算比较协议（另备，不替代自然结束比较）

- 各算法从**共同公共入口**用单调时钟记录"候选接受事件"，
  避免重复出现"P2 日志缺公共时间偏移"的问题；
- 截止前**完整合法**候选与截止后输出分开记录；
- 报"预算内最好完整候选的步数"和"截止时刻"两张表。

## 13. 决策规则（预先写死，不许事后改）

1. **P2 与强参照接近且更快** → 可以保留为底层，不为"创新"名义强改算法；
2. **P2 主要耗时在构造/距离** → 先区分工程优化与规划机制改进，前者不能冒称算法创新；
3. **P2 有稳定质量差距** → 依据坏例结构判断换底层还是改搜索，不看单个正例；
4. **某文献方法整体更合适** → 先用可信适配，再针对可复现瓶颈设计改进和消融；
5. **多方法互有优势** → 按问题条件分析取舍，不先加"万能选择器"扩大任务。

## 14. 本轮就把话说清楚的三件事

1. “多走 10%—20%、省时 80%—90%”**只是讨论过的假设**，不是验收指标；
2. 既有最好可行路线**不是**全局最优；跨方法最好值只能作已知参考；
3. 微图步数（`artifacts/runs/micro_runs.json`）只是正确性证据，
   **不能**当作性能排名，也不构成本协议的预跑结果。
