## R2 ε* 没有执行公共时间上限

**结论**：已修，并区分"协作式软截止"与"外部硬看门狗"。

**证据**：`tests_v02/test_r2_deadline.py`（9 个用例）、`src_v02/deadline.py`

**复现**：

```powershell
Set-Location "$R\tests_v02"
& $py -B -X utf8 -m unittest test_r2_deadline -v
```

**实测**：

| 用例 | 结果 |
|---|---|
| 假时钟（每次调用 +1.0 s）配 `time_limit_seconds=1e-9`，5×5 全目标 | `deadline_before_complete_route`，`route=()`，`natural=False`，`meta.deadline.soft_deadline_hit=True` |
| 同一实例、30 秒上限 | `finished`、审计合法、未触发截止 |
| 截止停止的原因 | 不等于 `FN_no_unexplored_cell` / `FN_no_positive_potential` |
| 6×6 大一点的实例被截止打断 | 若有路线，则审计必然不合法且含 `coverage_omission` 或 `missing_return`（不把截止后补的返航当候选） |
| 外部硬看门狗 | 子进程无限循环在 2 s 处被 `subprocess.TimeoutExpired` 杀死 |
| 软截止让子进程在外部上限内返回 | 12×12、2 ms 上限的子进程 20 s 内返回，状态为 `deadline_before_complete_route` 或 `finished` |

**`state_cycle` 的处理**（评审要求"标为人为安全截断并解释，或给有依据的终止策略"）：

- 状态键从 `(位置, 覆盖数量)` 扩展为 `(位置, 覆盖数量, 上一航点, 朝向)`；
- 终止名仍是 `state_cycle`，但 `trace.failures` 明确写入
  "artificial safety truncation: state key repeated …"，`etm.summary().terminal` 保留该名；
- 适配器把它映射为 `finished_with_safety_limit`（若路线完整）或
  `safety_limit_before_complete_route`，`natural` 一律为 False；
- **明确声明它不是原论文 ETM 的自然结束**，仍不是完整控制器状态（RNG、地形内部状态缺失），
  因此只是安全网，不声称"所有此类停止都保住了合法解"。

## R5 检查器和交接的证据口径不足

**结论**：四项全部处理。

### R5.1 成功必须所有合法性条件成立

`verify_v02.py::grade()` 是唯一的语义门：成功状态必须 `audit.valid`（含合法运动、返航、
完整覆盖、资源满足），否则至少报一条违规。检查器还内置**负例自检**：
"finished + 覆盖完整 + 超资源" 的记录必须被拒。

**复现**：

```powershell
& $py -B -X utf8 "$R\tests_v02\test_r5_semantics.py"     # 或
Set-Location "$R\tests_v02"; & $py -B -X utf8 -m unittest test_r5_semantics -v
& $py -B -X utf8 "$R\verify_v02.py"                       # 内建自检
```

**实测**：`success_status_over_resource`、`success_status_with_invalid_audit`、
`success_status_without_full_coverage`、`success_status_with_illegal_movement`、
`environment_infeasible_with_a_route`、`truncated_status_marked_natural` 都能触发；
正常记录不被误拒。

### R5.2 账本核验

`verify_v02.check_ledger()` 检查：`run_id` 唯一；`plan_id` 与任务集哈希非空；
正式批次的 `plan_id` 集合与 `run_manifest_v02.json` 的计划集合完全一致（缺失/多余都报）；
同一批次内不得重复登记同一格；每行的 `task_set_sha256` 与清单一致。

**实测**：`formal=102`、`test=60`、`development=13`、`unregistered=0`；
`test` 行随测试次数累积（每跑一次测试再追加 60 行）；`run_id` 全部唯一；正式批次 `missing=0 / extra=0`。
账本被标记为 `append_only`：`verify_v02.py` 校验它的**不变量**而不是哈希，所以在封存件上重跑测试不会让它失配。

### R5.3 调用数不再靠"登记数"充当总数

v0.2 把记录器放在 `adapters/registry.py::run`，**每一次**规划器调用都会写账本
（含 `kind`、`run_id`、`plan_id`），因此测试与开发调用也被登记；
`DSH_RUN_KIND` 或 `CONTEXT` 决定分类，未分类会写成 `unregistered` 并被检查器点名。

对 v0.1 的历史数字，本文件明确写：**无法恢复**。v0.1 的 408 只是 4 批 runner 的登记数，
不包含当时测试与 C* 开发迭代的调用；那部分数量**未知**，不虚构。

### R5.4 "状态与路线完全相同"改为逐案例矩阵

原先的表述不准确。准确表述与证据：

> 路线复用一致：102/102 条路线与 v0.1 相同（84 条非空逐格相同，18 条双方皆空）。
> 引擎原始状态被保留；2 个案例的对外状态被适配器归一化，逐条列在矩阵里。

**证据**：`evidence/behavior_matrix.csv`（102 行，含 `v01_status`、`v02_status`、
`status_same`、`route_same`、`both_empty`、`normalisation`）。

两处归一化：

| 案例 | 方法 | v0.1 | v0.2 | 原因 |
|---|---|---|---|---|
| `m12_resource_tight` | `PPCPP_CORE4` | `no_legal_candidate` | `no_legal_route_within_resource` | 直接返航就超预算，原因是资源而不是"没候选" |
