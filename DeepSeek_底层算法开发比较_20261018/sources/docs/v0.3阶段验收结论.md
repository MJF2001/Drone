## 不阻塞本阶段、但进入正式冻结前应清理的事项

1. registry.METHODS中ε*和C*的version/source仍有v0.2字符串，而实际ε*结果版本为v0.3。下轮冻结时统一注册表、实际入口、源码哈希和结果版本，不能用describe()旧标签代替真实来源。
2. verify_v03.py虽标只读，check_self_tests实际会在scratch创建、改写并删除_seal_probe.txt。它没有修改封存结果，但严格说不是零写入检查器；下轮将写文件自测移到测试套件，或明确标“只读封存证据、临时写scratch”。
3. 空任务连接跨截止时，run()的异常处理将route清空，因此不保证所有迟到路线都被保存在meta.diagnostic_route。审核跨截止的诊断保留已有测试，不能将此推广到所有分支。当前评分排除正确；保留诊断信息是下一步的小修，不应因此重新做整批实验。
4. 交付自带检查器没有完整读取汇总表做交叉关联；本次主会话已经独立补查且通过。正式运行前把这项关联纳入自动检查；同时校验start/end顺序和共有字段、方法版本与时间字段，避免过度宣称现有检查器能抓住所有篡改。
5. 硬终止测试实际验证的是子进程持久化start后被杀，审计能识别孤立start；并非已经测试所有规划器/本机原生依赖的硬终止行为。正式运行器仍需配置独立看门狗与失败记录。

上述内容不推翻A/B/C主要反例已修复及现有数据关联一致的结论，不再单开一轮大批修订任务，可纳入下一轮协议与运行器冻结。
