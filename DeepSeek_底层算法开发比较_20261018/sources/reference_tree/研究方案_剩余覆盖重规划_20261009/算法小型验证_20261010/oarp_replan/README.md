## 求解器与安装

实际使用Python 3.12、PySCIPOpt 6.2.1、SCIP 10.0.2、numpy 2.5.4。GLNS使用作者维护的C++端口0.1.0，commit `7804f7c65c66ddd13a12107163884ca334f8f93f`，源码在`../vendor/glns-cpp`，保留Apache-2.0许可证。依赖安装在`../.deps`，不修改系统Python。

入口先导入本包，以加载本地依赖路径。

```powershell
python -m pip install --target .deps pyscipopt==6.2.1 numpy==2.5.4
python -m pip install --target .deps --no-deps "git+https://github.com/stephenlsmith/glns-cpp.git@7804f7c65c66ddd13a12107163884ca334f8f93f"
```

C++扩展构建需要C++17编译器；本机Visual Studio工具已成功构建。不要将作者维护的移植版本称为原论文使用的Julia程序。GLNS采用default模式，5次cold trials、3次warm restarts，其余默认设置；固定种子按1000+案例序号，墙钟限时仍可能影响可复现性。

## 条带不能简单按方向再次合并

最小条带分区时，同方向邻格自然倾向合并。但新增条带预算很紧时，模型可能保留相邻同方向条带之间的旧切口，以保留旧条带身份。解码必须使用匹配/端点变量，不能只读横纵方向后强制合并。

穷举检查器因此枚举的是不重叠直线条带的完整划分，包含相邻条带之间的切口，不只是每格横纵方向。552个模型/预算核验组合包括504个小形状组合和48个混合旧方向、障碍/扩展组合。

## 合法性修正：必须保留这一说明

直接实现原文下界式与端点匹配时，在所测48个混合方向组合中，有2个得到不能解码成完整覆盖的整数解。具体输入见decoder_counterexample.json，比较记录见mixed_orientation_validation.json。

本实现不会将这类解当成覆盖路线。默认流程：原文形式LP→检查所有变量整数性→必要时整数规划；检查端点对应的条带是否精确覆盖且目标/预算一致。若解码仍不合法，启用**显式标记的合法性强化模型**重新求解。ILP-1强化约束要求选中区间对每个定向格恰覆盖一次；ILP-2强化端点与方向及相邻切口的守恒关系。

这部分是本地实现的修正，不宣称原论文已给出。`certification_repair`和`rejected_original`保留在结果中。设置`allow_certification_repair=False`时会返回`invalid_original_model_solution`，不偷偷修正。当前64例标准对照均未触发该修正，也没有触发整数回退。

这一发现只能说明本地依据公式实现的某些边界解需要额外核验；尚未获得作者实现或作者确认，不能写成“发现论文错误”，更不能直接当论文创新。

## 三类状态不要混淆

- 条带预算下无可行划分：该核心模型在当前预算下无解，不表示巡检任务不可达；适配器可使用已经生成的合法备用路线。
- 超时：仅接受在截止前已核验的候选，不能把未返回路径称为完成。底层求解器检查限时有开销，记录实际超时量，不宣称硬实时。
- 环境不可达：由共同地图与覆盖规则预检查，和模型预算/计算超时分开。

已完成：两种分区模型、端点/新增预算、旧段访问单元、方向与顺序GTSP、实际路径、合成原生演示、当前场景的完整规划接口与64例对照。

当前64例全部给定5秒，但实际两种模型的预算上限均为43、约束没有取等；不能据此声称已经实验证明预算机制有优势。预算机制正确性由紧预算小例验证，性能价值尚需单独实验。
