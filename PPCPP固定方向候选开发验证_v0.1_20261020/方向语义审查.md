## 2. 可能产生方向偏好的地方

core.reward_options先按坐标排序邻居；距离奖励取到空间捕食者的欧氏距离并在当前邻居内归一化，直行奖励来自previous→current与current→next的点积，边界奖励来自pending四邻接计数，权重固定(2,0.5)。共同旋转下，这些数学距离/点积/邻接量不变，不能把它们说成新奖励。

choose_neighbor以(-score, cell)择优，同分由字典序坐标决定。native.solve无局部候选时以(图距离, 坐标)选恢复目标。UnifiedGeometry.path虽与距离查询先后无关，却按旋转坐标系内的端点字典序固定方向；底层A*的堆键也包含坐标。字典序不是四旋转等变的tie规则，因此仅凭距离/奖励等变不能证明完整路线等变。恢复连接的几何同长tie、目标顺序、历史朝向与之后的采集过程可能相互影响，但本轮没有求解证据证明会获益。

model.adjacent枚举东、北、西、南；集合四邻接在90度旋转下仍相同，枚举顺序本身不等于已证实的方向收益。目标与历史作为集合时只变坐标；old_route作为时间序列不改时间顺序。原PPCPP使用H/current/previous，保留完整输入但不使用old_route优化；P2利用旧后缀是方法差异，不能重新生成历史去迎合方向。

障碍禁飞、目标遮挡/暂缓、图连通性、图距离、单格采集和返航到base在刚体整数旋转下保持。策略上也不能把已遮挡未采格计入H。四候选必须各从同一真实状态开始，不能接续前一候选采集；但本轮尚未实现候选或缓存封装。

## 3. 捕食者语义及阻断反例

当前数据的predator是**空间化算法输入**，不是本轮存在真实敌方物体的物理主张。已见54输入都由新图spec.case固定写入(-1,0)，实际runtime原样传入native.solve；不是每次求解按新坐标框架自动生成。spec.py:27是输入生成证据，不是可在旋转后任意重新生成输入的授权。

旧核心文件确实还定义了predator_for(targets,base)，但当前独立v0.2的solve没有调用它。不能因为同文件存在该旧函数，就把本次输入捕食者换成它的输出，再称冻结入口未变。

**决定性条件在实际ppcpp.py第19行：**

```python
if s.free and not (predator[0]<min(x for x,y in s.free) or predator[0]>max(x for x,y in s.free)):
    raise ValueError('predator outside fixed flight-domain x bounds required')
```

它要求捕食者严格位于飞行域x范围外，而不只是“不在F内”。当前54输入的F最小y=0，捕食者y=0。一致旋转90/270后，捕食者仍在图外，却落在旋转域x范围的边界，违反这个条件。按冻结源码表达式做整数算术核对得到：

|方向|满足当前捕食者x条件|不满足|规划器调用|
|---|---|---|---|
|0°|54|0|0|
|90°|0|54|0|
|180°|54|0|0|
|270°|0|54|0|

这不是216次规划器调用、异常日志或B2方向门槛；它是54输入×4方向的边界算术审查。没有实际调用solve去触发ValueError，observed_runtime_exceptions=0；实际预测依据是未修改的源表达式。

固定首例small_I_straight_p30：F包围盒x=0..14、y=0..10，pred=(-1,0)。90°先映射(-y,x)，共同平移(10,0)后F的x=0..10，pred=(10,-1)，pred.x等于x上界，条件不满足。270°共同平移后pred=(0,15)，x等于下界，也不满足。180°共同平移后pred=(15,10)，x>14，满足。此结论不依赖获益状态筛选。

共同平移不能修复：p.x<min(F.x) 与 p.x+t.x<min(F.x)+t.x完全等价，右侧同理。旋转中心换位置只增加共同平移，也不能修复。捕食者“仍在图外”与“在x范围外”是两种不同接口条件。

重置predator=(-1,0)、改为predator_for、只给门槛传虚拟域/不同捕食者、跳过第19行、直接改用旧core_route或减少为0/180两方向，都会改变本次指定语义或固定四候选协议，不能自行实施。
