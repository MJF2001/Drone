## 3. 先解决公平性：原始状态与评价状态分开

P2原生可以在搜索截止时返回此前接受的合法完整路线；PPCPP/LAST当前整体晚到会清空正式route。不能把P2的 `status=deadline` 一概算成没有路线，也不能把迟到路线当按时返回。

**不修改任何方法的原生返回策略，不给PPCPP/LAST添加P2保底，也不去掉P2保底。**

共同记录：

```text
native_status              原始求解器状态
has_returned_route         原始返回route是否非空
route_valid                独立核验完整覆盖、通行、返航、距离预算
entry_seconds              完整共同入口时间
timely_valid               route_valid且entry_seconds < 名义预算
late_valid                 route_valid但entry_seconds >= 名义预算
overrun_seconds            max(0, entry_seconds - 名义预算)
overrun_gt_10ms             是否超过预算10ms
route_source               P2保底/搜索候选，或LAST P0/P1
```

截止前内部接受某候选与完整入口按时交付是两回事。若原P2提供接受时间，可辅助报告，不能用它替代实际返回时间。不从中间trace“捞出”原方法未返回的路线。

报告必须并列两种视图，不能只挑对某方法有利的一种：

- **实际交付视图**：所有调用的及时合法率、失败/迟到及超时量；步数配对仅在双方及时合法时比较，并明确分母。没有及时配对则说无法判断，不能宣称某方法路线胜出。
- **原生软截止返回质量诊断**：在双方返回合法路线的配对中比较步数，保留实际耗时、迟到状态和分母。这不是严格截止下的胜率。若P2普遍贴线或迟到，必须解释其原生预算耗尽与返回/编码成本，不能利用这一点宣布LAST全面优越。

两个视图分别分析1秒、20秒，禁止把缺失/失败当0步或把成功子集直接称全批优势。

## 4. 共同入口与P2适配

三方法统一暖入口，包含输入解码、契约验证、Snapshot构造、求解全部工作、算法内部合法性检查和完整原始输出JSON编码；进程启动、导入、磁盘与独立事后审计在外。

PPCPP/LAST保持已审核入口范围。P2需要特别处理：

`baseline_suite.solve`在设置内部seconds之后还执行独立audit。若直接对整个函数调用计外部墙钟，会把该独立外审额外计入P2、与其他方法不一致。

优先建立透明P2薄适配器：

1. 共同入口内调用同一 `check_contract`。
2. 把剩余预算传给冻结 `p2_search_audit.solve(s, remaining, 'multi', seed)`。
3. 原有 `offer` 内部检查必须保留。
4. 复现环境不可行ValueError的原包装状态处理；不改变其异常、搜索顺序或返回保底。
5. 原始结果编码完成记录entry_seconds；独立外审随后执行。

适配器不称“原函数字节完全未动的直接调用”，明确它绕过的只是外部audit包装，并提供diff与门槛。若无法证明等价，停在接口审核交付，不能擅自改P2核心开始排名。

相同完整输入对三方法公开，包括原历史和旧后缀。P2利用旧后缀、原PPCPP不使用某些字段属于方法差异，不人为抹掉。P2随机种子、搜索轮数、多初始解配置及缓存均按冻结版本不变。

总预算是最大可用时间，不要求已结束方法空等到预算，不把相同上限误称相同实际CPU用量。所有内部余预算传递、预处理及编码都列清楚。

固定矩阵结束即停，不追加OARP等方法、不换种子/图/预算、不回头调LAST或P2。

可能结论均接受：

- LAST多数情况下不如P2：原PPCPP上的改进成立，但不足以支持强主算法竞争力；报告差距，不立即加规则追赶。
