# 途中已经完成覆盖，是否还需要完整执行后续条带？

日期：2026-10-10。单格正下方采集模型；探索性诊断，不是新算法的有效性证明。

## 1. 核心判断

**确实存在多余执行。** 冻结上一轮的独立条带、访问顺序与方向，仅跳过已经被实际飞行轨迹覆盖的目标点，两个条带模型各64例中都是37例缩短、27例不变、0例变差。

但这是一项应统一使用的覆盖进度处理规则，**不宜直接作为论文创新点**。我们的 P2 牛耕重建基线原本已经会跳过途中完成的目标访问，OARP 场景适配原本强制完整执行条带，两者存在这一执行规则差异。本轮正是在隔离并缩小这项差异。

处理后，模型2加共同备用路线相对 P2 为17胜、20平、27负。总步数降低约1.72%，但仍靠少数大幅收益案例拉低总数，尚未形成稳定优势。

## 2. 通俗解释

下面是自建说明例子，不是文献原图或原实验。

一条直线上的位置为 `0—1—2—3`，无人机在0，终点在3，待检点为1和2。原访问顺序先2后1。

- 完整执行：`0→1→2→1→2→3`，共5步。
- 利用途中覆盖：到2时，1已经在刚才的飞行途中检查过了，所以直接去3，`0→1→2→3`，共3步。

**跳过的是重复采集要求，不是禁止再次经过已检查位置。** 如果绕障碍或返航必须经过原位置，仍然允许经过。

## 3. 实验如何控制变量

输入为 run17 保存的128组独立条带访问解，来自64个环境快照、两个条带模型。它们不是128个独立地图；上一轮有62/64例条带划分相同。

固定以下内容：

- 地图、障碍、目标台账、已完成覆盖、当前位置、返航位置、资源上限。
- 条带划分、条带访问顺序以及每条条带的方向。
- A*实现与查询缓存预热顺序。两种处理各自新建 Geometry，并以相同 GTSP 矩阵构造预热缓存，避免仅由等长路径的缓存顺序造成差异。

不重新求解条带模型，也不重新调用 GLNS。

FULL：依次执行全部条带采集点。

SKIP：保持同一条采集点序列，只有确认某点已经被当前实际飞行轨迹覆盖，才跳过该点的服务要求；其他点仍按原顺序访问。连接继续使用 A*，最终返航。

仅对独立条带做这轮验证。没有同时修改旧路径段的内部连接，避免与第22份报告的约束解除混在一起。

单格采集下，访问目标所在格即可完成该格采集；经过时同样计入采集成功。**这是当前仿真模型，不代表真实无人机在任意速度经过时都能获得合格照片。** 本轮不引入视觉或飞行动力学。

## 4. 结果

| 指标：每组64例 | 模型1 | 模型2 |
|---|---:|---:|
| 纯核心路线：缩短 / 相同 / 变长 | 37 / 27 / 0 | 37 / 27 / 0 |
| 原完整执行总步数 | 10116 | 10112 |
| 跳过已完成服务后总步数 | 9992 | 9990 |
| 纯核心减少步数 | 124 | 122 |
| 加共同备用路线后，进一步改善例数 | 31 | 31 |
| 加备用路线：处理前总步数 | 10076 | 10072 |
| 加备用路线：处理后总步数 | 9972 | 9970 |
| P2总步数 | 10144 | 10144 |
| 处理后对 P2：胜 / 平 / 负 | 16 / 21 / 27 | 17 / 20 / 27 |

两组各有57例实际跳过了至少一个采集访问，但只有37例减少步数。原因是有些被跳过点本来就位于必经路径上；减少采集要求不一定缩短飞行路线。

相对 P2，模型2收益最大的三例分别少128、124和88步，合计340步。全部64例仅净少174步；除这三例外，其余61例合计多166步。因此不能只展示总步数，更不能宣称普遍优于牛耕重建。

仍然较差的案例：`v3_open_straight_L24_W9_p25`，原独立条带路线285步，跳过重复服务后281步，而 P2为259步。重复执行只解释了4步，仍有22步差距。

另一个案例：`v3_open_corner_channel_L24_W9_p25`，原379步，处理后371步，P2为499步。这个构造场景有较大优势，但不能代替对其他场景的检查。

## 5. 验证与适用边界

256条路线全部通过独立合法移动、障碍、目标覆盖、返航、资源和暂缓目标检查，0错误。FULL的128条路线与 run17 保存的参考路线逐点一致。

独立校验按原采集点序列推进实际轨迹，核对735次跳过记录：每个点在跳过发生前确实已经完成覆盖，而不是“未来会经过”就提前删除。所有待检点仍然在同一原始服务序列中。

两个专门的小测试通过：途中覆盖可以避免回头；尚未覆盖的目标不能被跳过。

本轮没有新求全局最优。上一轮“固定块模型达到精确最优”的结论仍然仅适用于完整执行模型；加入途中覆盖后，服务代价依赖此前轨迹，不能继续把旧 GTSP 精确值当成当前覆盖问题的最优值或下界。

本轮记录的时间只包括缓存预热后的路线后处理，不是总规划时间，不用于与 P2 做速度排名。当前仍是单次探索性实验，没有未见地图验证、真实续航验证或实际施工效果验证。

## 6. 接下来如何判断路线

现在已经确认两项来源：固定旧路径段会限制优化自由度；强制执行已完成服务会制造重复。这两项应保留为共同的适配规则，不再反复包装成新方法。

**我的建议是先停止给当前方法叠加小修补，下一步核查条带划分目标与真实步数目标是否错配。** 原方法的条带数量目标有其减少转弯的意义，但我们当前优化的是剩余移动步数。条带少，未必从当前位置连接起来更短。

先挑选上述仍输给 P2 的代表例，检查两者条带方向、入口位置、连接绕行和重复路段，区分“划分限制”与“访问排序求解不足”。较大实例目前没有全局精确解，不能预先把全部剩余差距归因于划分。根据诊断再提出有限个候选修改，同时保留树/图路线作为独立候选，不因当前已投入 OARP 实现就默认选它。

之后新增未参与设计的地图和种子，比较完整算法、共用预算及失败率。目前64例已经参与分析，不能充当最终独立测试集。
