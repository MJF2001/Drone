# 中等规模：计算预算与路线质量诊断

日期：2026-10-11。24个固定快照、3种方法、5个预算档位、2次重复，共720次求解。

## 1. 结论先说

**这次找到的是明确的实现层面预算敏感性，而不是已成立的算法创新。**

强基线P2_SHARED在0.1秒预算下，21/24个快照的两次运行都比同种子的20秒结果更长；48次运行汇总多走约13.8%。在5秒预算下，48次结果都与对应20秒结果相同。

条带候选在0.1、0.5秒的汇总步数较少；到2秒，强基线略胜；5秒时强基线明显更好。因此“哪个方法好”取决于可用计算时间，短预算下有待分析的质量损失。

**尚不能宣布真实无人机必须0.1秒完成重规划，更不能把Python实现的耗时直接当作问题本身的算法瓶颈。** 下一步先做耗时来源审计，排除可修复的基线实现低效，再判断是否值得研究结构复用或增量规划。

## 2. 实验设计

复用第25轮已经冻结的24个中等规模快照，避免换地图同时改变预算而混淆原因。它们现在是开发/诊断数据，不是新的独立测试集。

剩余目标数30—244，合法飞行格313—798。24个快照来自8组历史，每组3种事件，存在相关性。

预算档位：0.1、0.5、2、5秒，另加20秒长预算参照。三种方法仍为P2_SHARED、STRIP_HV、TREE_MST，代码不变，公共备用路线生成规则不变。

每个快照、每个档位、每种方法执行两次。GLNS种子为 `6000+10×快照编号+重复编号`，同一次重复跨预算保持一致。预算顺序循环轮换，第二次反向；方法顺序也轮换，减少固定执行顺序影响。

预算包含几何初始化、可达性、公共备用路线生成、搜索及候选合法性检查。最终独立审计不计入规划时间。所有限制仍为软限制，并非实时控制保证。本轮没有超过预算10毫秒的记录。

## 3. 核心结果

每个单元格汇总24个快照×2次运行，共48条路线。所有档位全部返回有效完整路线，所以这些总步数可以在本轮内直接比较。

| 预算秒 | P2_SHARED总步数 | STRIP_HV总步数 | TREE_MST总步数 |
|---|---:|---:|---:|
| 0.1 | 7700 | 7276 | 7820 |
| 0.5 | 7398 | 7086 | 7670 |
| 2 | 6988 | 7002 | 7220 |
| 5 | 6768 | 7002 | 7116 |
| 20 | 6768 | 7002 | 7116 |

0.1秒时，条带候选相对强基线在48次配对中38次更短、7次相同、3次更长，汇总少约5.51%。5秒时则是7次更短、9次相同、32次更长，汇总多234步。

这是候选表现随预算交叉的证据，不是“按预算切换方法”已经具备创新性的证据。把本轮每个实例的最好结果事后选出来，也不是可部署算法。

### 同一方法、同一种子与20秒配对

| 方法 | 较短预算 | 更差 / 相同 / 更好，共48次 | 配对净增步数 |
|---|---:|---:|---:|
| P2_SHARED | 0.1秒 | 42 / 6 / 0 | 932 |
| P2_SHARED | 0.5秒 | 23 / 25 / 0 | 630 |
| P2_SHARED | 2秒 | 6 / 42 / 0 | 220 |
| P2_SHARED | 5秒 | 0 / 48 / 0 | 0 |
| STRIP_HV | 0.1秒 | 22 / 26 / 0 | 274 |
| STRIP_HV | 0.5秒 | 6 / 42 / 0 | 84 |
| STRIP_HV | 2秒 | 0 / 48 / 0 | 0 |
| TREE_MST | 0.1秒 | 44 / 4 / 0 | 704 |
| TREE_MST | 0.5秒 | 29 / 19 / 0 | 554 |
| TREE_MST | 2秒 | 6 / 42 / 0 | 104 |

三种方法在5秒与20秒下均逐次相同。不能解释成已经达到全局最优：它们的搜索流程有固定的迭代/停止规则，结束后不会因为还有时间就无限增加搜索。20秒只是给同一流程更宽松的上限。

### 两次重复是否一致

P2_SHARED相对自身20秒结果：

- 0.1秒：21个快照两次都更差，3个两次相同。
- 0.5秒：11个两次更差，12个两次相同，1个重复间结果不同。
- 2秒：3个两次更差，21个两次相同。
- 5秒：24个两次全部相同。

两次重复支持本轮方向一致性，但不足以做稳定性置信区间或推广到其他机器。

## 4. 超时与巡检失败不是一回事

720次执行全部返回合法完整覆盖返航路线。0.1秒时，P2有42/48次搜索在预算耗尽时结束，TREE有44/48次，STRIP有28/48次；这些记录状态为“限时结束且已保留路线”，不是无路线。

P2的0.1秒结果中，26次最终仍采用公共GD备用路线，22次采用搜索改善结果。说明有些短预算执行来不及取得足够好的改善，但仍有可执行的任务路线。

没有无路线记录被删掉，也没有将无路线计为零步。专门测试覆盖了这种统计错误，以及“短预算偶尔可能更好”的记账情形。本轮恰好没有后者，但程序没有强制隐藏它。

## 5. 长预算路线到底有多接近最优

20秒结果不是最优证书。另将全部方法、预算和种子中每个快照的最好合法路线汇总为“最好已知可行参照”，每条都保存具体路线与来源记录。它只用于离线评价，不提前提供给待比较算法。

对每个快照，另算严格但可能偏松的下界：

`到第一个剩余目标的最小距离 + 剩余目标数−1 + 最后目标到基地的最小距离`

再按四邻接栅格的起终点颜色奇偶性向上修正。下界不要求条带连续，不会把未完成任务删除。

按每个快照计一次：

- 下界合计3128步。
- 最好已知可行路线合计3336步。
- P2的20秒路线合计3384步，两次结果相同。
- 2个快照的可行路线达到下界，因而这2例可以证明最优；其余22例不能。

因此P2在这批快照上的总最优差距介于48与256步之间：至少存在48步已被其他合法路线改善，最多可能有256步差距。**上下界之间的208步不是已经证明可节省的空间。** 这些合计是固定数据上的诊断值，不是现场收益预测。

## 6. 为什么不能马上当作创新点

目前至少有四个解释需要区分：

1. 原问题在较大目标规模下确实需要更有效的搜索。
2. P2的Python距离查询、候选构造或2-opt实现有工程低效，优化代码即可改善。
3. 条带候选的核心GLNS由C++执行，而P2、树构造和2-opt主要是Python。相同墙钟预算下的结果有实用比较意义，但不能只归因于算法思想优劣。
4. STRIP实现保留固定50毫秒后处理余量，短预算下占比很大；该分配规则本身也会影响结果，不能当作最优预算分配。

本轮没有记录各阶段耗时，尚不能断言成本集中在哪一步。也没有实测板载计算机或确认施工现场允许的反应期限。0.1秒、0.5秒是敏感性实验档位，不是已验证的作业需求。

## 7. 下一步的明确判断

**现在值得继续查计算瓶颈，但还不值得直接设计新的混合算法。** 小规模步数已基本饱和；中等规模出现了可重复的短预算质量损失，这是比“给条带加一棵树”更具体的线索。

下一步应对强基线做分阶段耗时与候选生成轨迹审计：何时得到第一条合法路线，何时改善，时间花在地图距离、最近邻、2-opt还是合法性检查。剖析运行产生额外开销时，不能把它的绝对耗时混入本轮公平比较。

如果主要差距来自可避免的重复距离计算或Python循环，应先修好强基线，再重测预算曲线。论文不能靠故意保留低效基线获得优势。

只有合理优化的强基线仍存在稳定的质量/时间缺口，才考虑“复用既有覆盖结构，在给定计算预算内更早得到低代价剩余路线”作为候选研究切入点。它仍需新地图验证、与已有增量/限时规划文献对照，不能承诺现在已经具有新颖性。
